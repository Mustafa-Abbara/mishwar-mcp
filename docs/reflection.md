# Reflection

I drew the lines between the tools by two questions: does the tool change anything, and is it one step or a whole workflow? `get_weather_forecast` only reads, `save_trip_plan` only writes, and `plan_day_trip` is the only workflow. The hardest call was geocoding. Turning "Byblos" into coordinates is technically a second job, but from the agent's side "forecast for a named place" is one request. Taking raw latitude and longitude, as notebook 7's server does, would push geocoding onto the LLM. So I kept it inside the Data tool, with a small alias table for local names like Jbeil. I also kept the go/no-go decision in code: a fixed rule table decides the verdict and the LLM only explains it, so the same forecast always gives the same answer and every rule has a unit test. Reading saved plans became a resource instead of a fourth tool, because it is a pure lookup the host can do itself.

Three tools felt right for this use case, and the evaluation backs it up. Routing accuracy was 100% over 22 runs, so the model never confused the tools. When I hid `plan_day_trip` and let the model chain the other two, it needed 2.7 LLM calls per plan instead of 2.0. It still followed the rules, but only on clear-cut forecasts, which is where I would expect its own judgement to drift least. The trade-off is that the orchestrator hides its steps from the model, so a user cannot ask it to "check the weather but use my own threshold". The evaluation also showed how fragile the edges are. The model asked for "The Cedars", and in one experiment it called a tool that was hidden, because my instructions still named it. Tool descriptions and agent instructions turned out to be one contract. As next steps, I would add a real notification action (ntfy or email), per-user stores with authentication so the HTTP server could be shared, forecast caching, and a separate `geocode_place` tool if the toolkit grew beyond Lebanon.
